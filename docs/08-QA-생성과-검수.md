# 08. QA 생성과 검수

답변을 만들고, 승인해서, 사용자에게 내보내기까지의 전 과정입니다.
**이 프로젝트의 전제를 지탱하는 단계**입니다 — 운영에서 답변을 만들지 않기로 했으므로
답변은 여기서 미리 만들어져 있어야 합니다.

← [07. 테스트](07-테스트.md) · 다음 [09. 화면](09-화면.md)

---

## 전체 흐름

```
① 생성 (studio)          문서/질문 ──LLM──> 초안        generated_qa.json
        ↓
② 반영                   초안 선택 ──> pending 으로      qa_index.json
        ↓
③ 검수 (사람)            읽고 고치고 승인 ──> approved   qa_index.json
        ↓
④ 색인                   approved 만 벡터 인덱스로       chroma/
        ↓
⑤ 서비스                 사용자 질문에 답변으로 나감
        ↓
⑥ 평가                   적중률·오매칭률 측정 → 임계값 결정
```

**③을 건너뛸 수 없습니다.** `approved` 만 인덱스에 올라가므로, AI 초안이 검수 없이
사용자에게 새어 나가는 경로가 **구조적으로** 막혀 있습니다.

## ① 생성 (studio 전용)

```bash
# .env
APP_MODE=studio
OLLAMA_LLM_MODEL=gemma4:latest
```

```bash
ollama pull gemma4

python scripts/generate_qa.py --max 3 --variants 12    # 소량으로 품질 먼저 확인
python scripts/generate_qa.py --apply                  # 초안을 pending 으로 반영
python scripts/generate_qa.py --category api_reg_flow  # 추천 질문에 답 붙이기
```

### 스크립트 옵션

| 옵션 | 기본값 | 설명 |
| --- | --- | --- |
| `--docs` | (전체) | 문서 ID 목록 |
| `--category` | — | 카테고리 ID — **추천 질문에 답변을 붙입니다** |
| `--model` | `.env` 값 | 생성 모델 |
| `--per-chunk` | 2 | 청크당 QA 개수 |
| `--variants` | 10 | 항목당 변형 질문 수 |
| `--max` | 50 | 최대 생성 항목 수 |
| `--apply` | off | 결과를 `pending` 으로 QA 인덱스에 넣습니다 |

### 두 가지 생성 경로

```
문서 청크 ─→ [LLM] ─→ 질문 + 답변 ─→ [LLM] ─→ 변형 질문 8~15개
질문 목록 ─→ 문서 검색 ─→ 발췌 ─→ [LLM] ─→ 근거 있음? ─→ 답변 ─→ 변형 질문
                                          └─ 없음 ─→ 버립니다
```

**문서에서 시작하는 쪽이 기본**입니다.

질문에서 시작하는 쪽은 "사용자가 실제로 물었는데 답이 없었던 질문"(질문 분석 탭)을 QA로
만드는 용도라 **근거가 없을 수 있습니다.** 그때 답을 지어내면 검수자가 사실 여부를 문서와
대조하지 못한 채 승인하게 되고, 이 서비스의 유일한 품질 보증인 '검수'가 무력해집니다.
그래서 모델이 `근거: 없음` 을 선언하면 **그 질문은 버립니다.**

> 1차 프로젝트에서 유사도 숫자만으로 판단했다가 "점심 메뉴 추천"에 억지 답변이 나간 적이
> 있습니다.

### 변형 질문을 따로 한 번 더 부르는 이유

**적중률은 사실상 변형 질문 목록이 결정합니다.**

| 질문 | 유사도 |
| --- | --- |
| "API 등록은 어떻게 하나요?" (대표 질문) | 1.000 |
| "등록하는 방법 알려줘" (변형에서 걸림) | 0.974 |

질문·답변과 한 번에 만들게 하면 모델이 형식을 지키느라 변형을 2~3개로 줄입니다. 호출을
나누면 항목당 10개 이상이 안정적으로 나옵니다. 어차피 스튜디오에서 도는 배치라 호출 수보다
결과 품질이 중요합니다.

### API로 (관리자 화면 탭 ⑥)

수십 분 걸리는 작업이라 시작·폴링·중지가 나뉘어 있습니다.

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/api/studio/generate` | 시작 (이미 실행 중이면 409) |
| GET | `/api/studio/generate/progress` | 진행률 |
| POST | `/api/studio/generate/stop` | 중지 — 그때까지 만든 초안은 남습니다 |
| GET | `/api/studio/generate/result` | 초안 목록 |
| POST | `/api/studio/generate/apply` | 선택 항목을 **pending** 으로 반영 |
| POST | `/api/studio/generate/variants` | 변형 질문만 추가 생성 |

serve 모드에서는 전 구간 **403** 입니다.

### 실측 (gemma4:latest, 로컬 PC)

| 항목 | 값 |
| --- | --- |
| 한 항목 생성 시간 | 약 1분 (본문 1회 + 변형 1회) |
| 항목당 변형 질문 | 8개 요청 → 7개 (중복·대표질문과 같은 것 제외) |
| 답변 길이 | 2~3문장 (규칙은 3~6문장인데 짧게 나오는 편) |
| `category_id` | 대부분 `null` — 문서 프론트매터 분류와 카테고리 이름이 정확히 겹칠 때만 채웁니다 |

### 주의

> **프롬프트를 고쳤으면 실제 모델로 소량(`--max 2`) 실행해 눈으로 보세요.**
> 테스트의 LLM은 가짜라 형식 이탈·문서 베끼기가 잡히지 않습니다.
>
> 실제로 도입부에서 **메타 질문**("이 문서는 무엇을 설명하나요")이 나오고, 답변에 **문서
> 내부 표기**(`[[api-등록]]`)가 새어 나온 적이 있습니다. 둘 다 막아 뒀습니다
> (`_is_document_lead`, `clean_answer`).

## ② 반영 — 언제나 `pending`

`apply` 하면 초안이 `qa_index.json` 에 **`pending`** 상태로 들어갑니다. 절대 바로
`approved` 가 되지 않습니다.

`generated_qa.json` 과 `qa_index.json` 을 **일부러 파일로 나눴습니다** — "사람 손을 안 탄
것"과 "검수 대상"이 파일 단위로 구분돼야 실수로 배포되지 않습니다.

## ③ 검수

### 어디서 하나

| 화면 | 성격 | 언제 |
| --- | --- | --- |
| 관리자 `검수` | **결재함** — 검수대기(pending)만, 한 건씩 | 매일 하는 승인 작업 |
| 관리자 `QA 인덱스` | **자료실** — 전체 목록·검색·일괄 처리 | 이미 있는 항목을 찾아 고칠 때 |

두 화면은 **같은 편집 컴포넌트**(`.admin_editor`)를 씁니다. 두 벌로 두면 한쪽만 고쳐지고,
검수자가 본 모습과 사용자가 보는 모습이 갈립니다.

**QA 인덱스의 편집은 serve 모드에서 읽기 전용입니다**(검수는 스튜디오에서 하고 결과 파일을
배포한다는 전제). 다만 **`검수` 화면의 승인은 serve 에서도 됩니다** — 운영에 쌓인 질문에서
만든 QA를 그 자리에서 승인해야 하는 경우가 있기 때문입니다.

> `/admin/review` 임시 화면은 **2026-08-16 에 걷어냈습니다.** 관리자 화면에 검수 항목이
> 생기기 전까지 승인 경로를 열어 두려던 것이었습니다.

### 검수 화면이 하는 일

- 상태 탭(검수대기 · 승인 · 보류 · 미사용) · 주제/검색/정렬
- 일괄 처리(승인 · 보류 · 미사용 · 삭제 · 주제 지정)
- **검수 모달** — 답변을 고치면서 **사용자에게 보이는 모습**을 바로 옆에서 봅니다
- 변형 질문 추가·삭제
- 출처 문서를 눌러 원문 확인

> 미리보기는 챗봇 말풍선과 **같은 렌더 규칙**을 씁니다. 다르면 검수가 의미를 잃습니다.
> `chat.js` 의 마크다운 렌더를 고치면 `admin.js` 도 같이 고쳐야 합니다.

### 검수할 때 볼 것

| 확인 | 왜 |
| --- | --- |
| 답변이 문서 근거와 맞나 | 지어낸 내용이 섞이면 검수의 의미가 없습니다 |
| 문서 내부 표기가 새어 나왔나 | `[[문서ID]]` 같은 것 |
| 도입부 메타 질문인가 | "이 문서는 무엇을 설명하나요" 류는 버립니다 |
| 변형 질문이 충분한가 | **적중률을 결정합니다.** 부족하면 추가 생성 |
| 주제(`category_id`)가 맞나 | 대부분 `null` 로 오므로 사람이 지정합니다 |
| 보류라면 이유를 `note` 에 | **안 남기면 다음 사람이 같은 판단을 반복합니다** |

### 상태

| 상태 | 뜻 | 서비스되나 |
| --- | --- | --- |
| `pending` | 검수 대기 | ✕ |
| `approved` | 승인 | **○** |
| `hold` | 보류 | ✕ |
| `disabled` | 미사용 | ✕ |

**답변이 이상하면 모델보다 문서를 먼저 의심하는 편이 빠릅니다.** 1차 프로젝트에서도 모델이
아니라 문서가 원인이던 경우가 있었습니다.

## ④ 색인

승인하면 저장소가 **파일을 먼저 쓰고 벡터를 나중에** 씁니다. 순서가 반대면 저장 실패 시
검색은 새 답변을, 화면은 옛 답변을 보여주는 상태가 됩니다.

변형 질문은 **먼저 지우고 다시 넣습니다.** upsert 만 하면 삭제한 변형 질문의 벡터가 남아
계속 걸립니다.

수동 재색인:

```bash
curl -u admin:비밀번호 -X POST "http://localhost:18100/api/admin/qa/reindex?include_docs=true"
```

## 품질 평가

흐름의 **⑥ 단계**입니다. 관리자 탭 ⑦ · studio 전용.

`qa_match_threshold=0.90` 이 맞는지 **숫자로** 확인합니다. 지금 이 값은 근거가 없습니다.

### 골든셋을 따로 만들지 않습니다

사람이 평가 문항을 손으로 쓰는 대신, **이미 검수해 둔 QA의 변형 질문을 그대로 문항으로**
씁니다. 변형 질문은 "이 질문이 오면 이 답이 나와야 한다"를 사람이 직접 확인한 것이라 정답
라벨이 이미 붙어 있는 셈입니다.

별도 골든셋 파일을 두면 QA를 고칠 때마다 따로 관리해야 합니다.

### 자기 자신에 걸리는 문제

변형 질문은 **벡터 인덱스에 이미 들어 있습니다.** 그대로 검색하면 유사도 1.000으로 자기
자신이 1등이 되어 적중률이 항상 100%가 나옵니다 — 아무것도 측정하지 못합니다.

그래서 검색 결과에서 **질문과 글자가 같은 항목을 걸러냅니다.** 남은 순위는 "이 표현이
인덱스에 없었다면 어떻게 됐을까"에 해당합니다.

(벡터를 실제로 빼고 다시 넣는 방법도 있지만, 문항마다 색인을 고치는 것은 느리고 도중에
실패하면 인덱스가 깨집니다.)

### 재는 것

| 지표 | 뜻 |
| --- | --- |
| 적중률(Top-1) | 1등이 기대한 QA인 비율 |
| 적중률(Top-3) | 상위 3등 안에 기대한 QA가 있는 비율 |
| **오매칭률** | 1등이 **다른** QA인데 임계값을 넘어 답변으로 나가는 비율 |
| 미검색 | 못 찾았거나 임계값에 못 미친 비율 |

결과에 **임계값별 표(0.75~0.95)** 가 함께 옵니다.

> **오매칭이 미검색보다 나쁩니다.** 못 찾으면 사용자가 다시 묻지만, 엉뚱한 답이 나가면
> 그것이 맞는 줄 압니다. 임계값을 내릴 때는 이 값을 먼저 보세요.

### 아직 숫자를 못 냈습니다

승인된 QA가 적어서입니다. QA를 쌓은 뒤 돌려 보세요.

임베딩 모델 비교(`bge-m3` vs `embeddinggemma`)도 이 표로 합니다.
**벤치마크 순위는 믿지 마세요** — 이전에 MTEB 순위가 이 프로젝트 문서에서 뒤집혔습니다.

## 답을 못 찾은 질문을 QA로 만들기

```
질문 이력 ──군집 분석(탭 ②)──> 비슷한 질문 묶음
                                     │
                                     ├─ 답이 있었어야 할 것 ──> QA 생성(탭 ⑥)
                                     └─ 문서가 없는 것 ──────> 문서 작성(탭 ⑤)
```

군집 분석은 **LLM을 쓰지 않습니다** — 답변할 때 저장해 둔 질문 임베딩을 재사용합니다.
그래서 운영에서도 돌아갑니다.

사람이 지정한 상태·주제는 따로 보관돼 다시 분석해도 남습니다.
군집 상태: `new` · `reviewed` · `generated` · `applied` · `excluded`
