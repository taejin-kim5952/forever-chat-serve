### 개발 PC 에서 실제로 재 본 값 (2026-08-17)

| | 값 |
| --- | --- |
| 빌드 시간 | 약 1분 30초 (`pip install` 37초 · 컨텍스트 전송 20초) |
| 이미지 (디스크) | **2.66GB** |
| `docker save` 결과 | **902MB** ← 옮기는 건 이만큼 |
| 첫 질문 | **9.7초** (ONNX 모델 적재 + Chroma 열기) |
| 이후 질문 | **31~55ms** — 컨테이너 밖에서 잰 값과 같음 |
| 헬스체크 | `healthy` (`/health/ready` → `status: ok`, `qa_serving: 7`) |

**첫 질문이 10초인 것은 정상입니다** — 모델을 그때 올립니다. 사용자에게 그 10초가 가지
않게 하려면 기동 직후 아무 질문이나 한 번 던져 두면 됩니다(워밍업).

### 도커여야 하는 이유 ★

개발 서버가 **CentOS 7(glibc 2.17)** 인데 `onnxruntime` 휠은 **glibc 2.28** 을 요구합니다.
호스트에 직접 설치할 수 없습니다(2026-08-17 PyPI 확인). 컨테이너는 자기 glibc 를 들고
오므로 상관없습니다. CentOS 7 은 지원도 끝났습니다.

```
onnxruntime 1.28.0  →  manylinux_2_28   ✗  CentOS 7
tokenizers · numpy  →  manylinux2014    ✓
```

### 이미지에 무엇이 들어가나

```
코드(app · scripts) + 파이썬 의존성 + 임베딩 모델 565MB     ← 이미지 (2.66GB)
data/ (qa_index.json · categories.json · raw_docs · chroma · 이력)  ← 볼륨
```

이미지가 2.66GB인데 모델은 565MB뿐입니다. 나머지는 `onnxruntime` 과 `chromadb` 의 의존성
입니다. 줄일 수 있지만 폐쇄망 반입이 902MB 한 번이라 지금은 손대지 않았습니다.

**모델을 이미지에 굽는 이유**는 폐쇄망 때문입니다 — 이미지 하나만 반입하면 됩니다.
**`data/` 를 빼는 이유**는 그 반대입니다 — 검수 결과와 질문 이력이 쌓이는 곳이라, 컨테이너를
새로 만들어도 남아야 합니다.

## 개발 서버에 올리는 절차

빌드는 **개발 PC 에서** 합니다. 폐쇄망 반입과 같은 방식이라 그 자체가 리허설입니다.

```powershell
# 1) 개발 PC — 빌드하고 여기서 먼저 띄워 확인
docker build -t openapi-chat-serve:latest .
docker run -d --name chat-smoke -p 18101:18100 -e ADMIN_PASSWORD=시험용 `
  -v "c:\chatapp\forever-chat-serve\data:/app/data" openapi-chat-serve:latest
#   http://127.0.0.1:18101/health/ready 가 status ok 인지 확인 (모델 적재에 10초쯤)
#   질문도 한 번 던져 봅니다:  POST /api/ask  {"question":"API 등록은 어떻게 하나요?"}
docker rm -f chat-smoke

# 2) 이미지를 파일로 — gzip 은 하지 마세요
docker save openapi-chat-serve:latest -o chat-serve.tar      # 902MB
```

`docker save` 결과는 **이미 압축된 레이어**라 `gzip` 을 걸어도 902MB 그대로였습니다
(2026-08-17 확인). 시간만 더 듭니다.

```bash
# 3) 서버로 옮기고 싣기
scp chat-serve.tar 사용자@서버:/tmp/
ssh 사용자@서버 'docker load -i /tmp/chat-serve.tar'

# 4) 서버에서 — data/ 를 먼저 올리고 소유자를 맞춘다 ★
#    qa_index.json · categories.json · raw_docs/  세 가지가 원본입니다
sudo chown -R 10001:10001 data/
docker compose up -d          # ADMIN_PASSWORD 를 환경변수로 주입
```

### `chown 10001` 을 빼먹으면 ★

컨테이너는 **uid 10001(appuser)** 로 돕니다. 윈도우 개발 PC 에서는 bind mount 가 전부
`rwxrwxrwx` 로 보여 그냥 됐지만, **리눅스 서버에서는 권한이 그대로 넘어갑니다.** 소유자를
안 맞추면 조회는 되는데 질문 이력·승인·설정 저장이 조용히 실패합니다.

### 포트를 127.0.0.1 에만 여는 이유 ★

개발 서버는 **인터넷에 노출돼 있고 SSH 실패 로그인이 2,600건 넘게 관측**됐습니다(아래).
시험 단계에서 굳이 열어 둘 이유가 없습니다. 접속은 터널로 합니다.

```bash
ssh -L 18100:127.0.0.1:18100 사용자@서버
```

`docker-compose.yml` 이 이미 `127.0.0.1:18100` 으로 묶어 두었습니다.

### 처음 띄울 때 막히는 곳

| 증상 | 원인 | 확인 |
| --- | --- | --- |
| 모든 질문이 `unresolved` | 벡터 저장소가 없음 | 재색인 API 한 번 |
| `/health/ready` 가 `degraded` | 모델 파일 또는 승인 QA 없음 | 응답의 `embed_model` · `qa_serving` |
| 기동은 되는데 답이 옛날 것 | `data/` 볼륨이 안 붙음 | `docker compose config` |
| 답은 나오는데 저장이 안 됨 | `data/` 소유자가 10001 이 아님 | `docker exec ... touch /app/data/x` |
| 첫 질문만 10초 | 정상 (모델 적재) | 두 번째 질문이 50ms 이하면 정상 |

1차 프로젝트 것은 [참고/이전프로젝트/deploy/](../참고/이전프로젝트/deploy/) 에 있고
**그 폴더는 실행되지 않습니다** — 전제가 다릅니다(아래 §이전 절차서). 참고만 하세요.

## 이전 절차서가 그대로 안 맞는 이유

`DEPLOY_AIRGAP.md` 는 **단일 서버 + Docker Compose + Jenkins + Ollama 3종** 전제입니다.

| | 이전 문서 | 현재 |
| --- | --- | --- |
| 인프라 | 단일 서버 Compose | AKS (매니페스트 미작성) |
| 오케스트레이션 | Jenkins 파이프라인 | 미정 |
| 컨테이너 | 앱 + Ollama **2개** | **1개** (임베딩이 앱 안에서) |
| 임베딩 | Ollama `bge-m3` 1.1GB | **ONNX int8 565MB, 이미지에 포함** |
| 답변 모델 `qwen3.5:4b` | 3GB | **불필요** |
| 채점 모델 `gemma4` | 9GB | **불필요** (studio 전용) |
| 반입 파일 합계 | 약 13GB | **이미지 1개 (약 1GB)** |
| 서버 메모리 최소 | 8GB | 2GB 수준 |
| `/admin` 인증 | **없음** | 있음 (세션 + Basic) |

**LLM과 Ollama가 통째로 빠집니다.** 모델 반입 절차, `OLLAMA_MAX_LOADED_MODELS` 조정, 모델
교체 시나리오, 사이드카 배치 고민 같은 절이 전부 필요 없어졌습니다. 반입물은 **이미지 하나**
입니다.

그래도 **Compose/Jenkins 절차를 AKS로 옮기는 부분**은 새로 써야 합니다.

## ★ 아직 안 정해진 것 — 파드를 늘릴 때 `data/` 공유

지금은 **파드 1개** 전제라 볼륨 하나면 됩니다. 늘리게 되면 아래를 정해야 합니다.

| 파일 | 성격 | 파드 간 |
| --- | --- | --- |
| `qa_index.json` · `categories.json` · `raw_docs/` · `profile.json` | 읽기 전용 (배포 산출물) | 같아야 함 |
| `chroma/` | 파생 | 파드마다 만들어도 됨 (기동 시간 ↑) |
| `question_log.jsonl` · `question_embeddings.jsonl` | **쓰기** | 합쳐져야 함 |
| `runtime_config.json` | **쓰기** (관리자가 바꿈) | 같아야 함 |
| `analytics.json` · `job_history.json` | 쓰기 | 같아야 함 |

선택지:

- **ReadWriteMany 공유 볼륨** — 가장 단순하지만 JSONL 동시 쓰기 경합을 확인해야 합니다
- **읽기 전용 + 쓰기 분리** — 원본은 이미지에, 쓰기 데이터만 공유 볼륨
- **관리자 전용 파드 분리** — 쓰기는 한 파드만

`SESSION_SECRET` 은 이때 **반드시** 지정해야 합니다 — 안 주면 파드마다 서명 키가 달라
관리자 로그인이 요청마다 풀립니다.

---

## 이미 정해진 것

| 항목 | 값 | 이유 |
| --- | --- | --- |
| `APP_MODE` | **`serve`** | 운영에 GPU가 없습니다. studio 라우터는 403 |
| `SESSION_SECRET` | **반드시 지정** | 안 주면 파드마다 서명 키가 달라 로그인이 풀립니다 |
| `ADMIN_PASSWORD` | **Secret 주입** | 기본값이면 기동 로그에 경고. 파일에 넣지 않습니다 |
| `LOG_FILE` | 기본값 또는 볼륨 경로 | 절대경로를 코드에 박으면 배포가 깨집니다 |
| 옮길 파일 | `qa_index.json` · `categories.json` · `raw_docs/` · `profile.json` | 나머지는 파생물이거나 운영 데이터 |
| `profile.json` | 납품처마다 다름 | 조직명·서비스명·도메인 소개·언어. 없으면 KT 기본값이 나갑니다 |

## 시드 디렉터리 패턴 (아직 안 넣음)

지금 `Dockerfile` 에는 이 패턴이 **없습니다.** `data/` 를 사람이 직접 서버에 올리고
bind mount 하는 방식이라(위 절차 4번) 당장은 문제가 되지 않습니다. **명명 볼륨을 쓰게 되면**
아래 문제가 그대로 생기므로 그때 넣어야 합니다.

이전 프로젝트에서 겪은 문제입니다.

> **Docker 볼륨은 처음 만들어질 때만 이미지 내용을 복사합니다.** 이미지 안 `/app/data` 에
> 문서를 두면 **두 번째 배포부터 문서를 고쳐도 반영되지 않습니다.**

해결:

```
이미지  /app/seed/     ← 원본 (문서·카테고리·QA)
볼륨    /app/data/     ← 운영 데이터

기동 시 entrypoint 가 볼륨에 "없는 파일만" 복사
```

결과적으로 **새로 추가한 문서·카테고리는 다음 배포에 반영되고, 관리자 화면에서 편집한
내용은 보존됩니다.**

강제 초기화가 필요하면 `SEED_FORCE=true` 를 한 번만 켰다 끕니다(켜둔 채로 두면 배포마다
편집 내용이 되돌아갑니다).

## 배포 후 확인

```bash
curl http://<서버>/health          # {"status":"ok"}
curl http://<서버>/health/ready    # embed_model=ok, qa_serving>0, status=ok
curl http://<서버>/api/categories  # groups 가 비어 있으면 안 됩니다
```

브라우저:

- `/` — 챗봇. **입력창 위에 `주제 선택` 버튼이 보여야 합니다** (안 보이면 카테고리가 빔)
- `/admin` — 로그인 모달이 뜨고, studio 전용 탭(⑤⑥⑦)이 **보이지 않아야 합니다**

첫 질문은 임베딩 모델 적재 때문에 느립니다 — 컨테이너에서 **9.7초**를 쟀습니다. 두 번째
질문부터 31~55ms 로 떨어지면 정상입니다.

## 관리자 접근 경로

파이썬 서비스를 내부에만 두면 관리자가 `/admin` 에 들어갈 길을 따로 만들어야 합니다.

- 인그레스에 관리자 경로만 열기 (사내망 IP 제한 권장)
- 또는 포트포워딩 등 운영 도구로만 접근

1차 프로젝트에서 `/admin` 이 무인증이었던 전례가 있으니 **노출면을 늘리지 않는 쪽**을
권합니다.

## 스프링 포털에 챗봇을 붙일 때

포털(`openapi-mng-dev-jdk21`)에서 페이지별로 챗봇을 띄우려는 계획이 있습니다. 방식에 따라
배포 구성이 달라집니다.

| 방식 | 인그레스 | CORS | 파이썬 노출 |
| --- | --- | --- | --- |
| **스프링 서버 경유(프록시)** | 변경 불필요 | 없음 | 내부에만 |
| 인그레스 경로 분리 | 규칙 추가 | 없음 (같은 호스트) | 브라우저에 노출 |
| 브라우저에서 직접 호출 | 규칙 추가 | **CORS 미들웨어 추가 필요** | 브라우저에 노출 |

현재 `app/main.py` 에는 **CORS 미들웨어가 없습니다.** 세 번째 방식을 택하면 추가해야 합니다.

`POST /api/ask` 는 이미 `category_id` · `user_id` · `channel` 을 받으므로, 페이지별
파라미터를 넘기는 데 API 변경은 필요 없습니다.
