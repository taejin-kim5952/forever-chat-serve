## 구성 — 서버가 **사내 AI 테스트 PC** 의 Ollama 를 봅니다 (2026-10-07 확인)

```
사용자 ─→ 개발 서버(컨테이너 1개) ─── 11434 ──→ AI 테스트 PC (Ollama)
                 │
                 └ 검수된 답변 · 질문 이력 · 자료는 서버 안에서 끝납니다
```

같은 사내망이라 됩니다. 1차(`forever-chat`)가 이미 이 방식으로 올라가 있습니다.
설정은 [.env.server.example](../.env.server.example) 에 따로 두었습니다.

**서버도 `APP_MODE=studio` 입니다.** 이 코드에서 모드는 "이 기계에 GPU 가 있나"가 아니라
**"이 설치가 LLM 을 쓰나"** 를 뜻합니다. `serve` 로 두면 `OLLAMA_HOST` 를 맞춰도
`/api/models` 가 빈 목록을 돌려주고 화면이 AI 답변 스위치를 잠급니다.

아래 '**LLM과 Ollama가 통째로 빠집니다**' 는 **운영(AKS) 기준**이고 개발 서버에는
해당하지 않습니다. 운영에 GPU 가 없다는 전제는 그대로입니다 — 그쪽은 검수된 답변만
나갑니다.

### AI 테스트 PC 가 꺼져 있으면

AI 답변만 멈추고 **검수된 답변은 그대로 나갑니다.** 화면이 모델 목록이 빈 것을 보고
스위치를 잠급니다. 그래서 서버에서는 `AI_ANSWER_DEFAULT=false` 로 두어 **검수된 답변이
기본**이 되게 합니다 — true 로 두면 그 PC 가 꺼지는 순간 모든 사용자의 기본 경험이
멈춥니다.

사용자가 여럿이면 그 PC 한 대가 **직렬로** 받습니다. 한 건에 6.8초(gemma4:latest,
2026-10-07 측정)라 세 명이 동시에 물으면 뒤 사람은 20초입니다.

### 개발 PC 에서 실제로 재 본 값

| | 2026-08-17 | 2026-10-07 |
| --- | --- | --- |
| 이미지 — 모델 없이 | — | **710MB** ← 개발 서버 |
| 이미지 — 모델 구움 | 2.66GB | **1.7GB** ← 폐쇄망 |
| `docker save` 결과 | 902MB | **528MB** ← 반입물 |
| 모델 받는 시간 | — | 100~170초 (빌드 안에서) |
| 첫 질문 | 9.7초 | 2.7초 (ONNX 적재 + Chroma 열기) |
| 이후 질문 | 31~55ms | **21ms** |
| 헬스체크 | `healthy` | `healthy` (`qa_serving: 55`) |

**반입물이 902MB → 528MB 로 줄어든 이유**는 모델을 두 번 넣지 않게 된 것입니다. 맨 뒤에서
`chown -R` 을 하면 소유자만 바뀐 파일이 새 레이어에 통째로 다시 들어갑니다(아래 'chown -R
을 뒤에서 하지 않습니다'). 압축도 줄이지도 않았고, 중복을 뺐을 뿐입니다.

**첫 질문이 몇 초 걸리는 것은 정상입니다** — 모델을 그때 올립니다. 사용자에게 그 10초가 가지
않게 하려면 기동 직후 아무 질문이나 한 번 던져 두면 됩니다(워밍업).

### 도커여야 하는 이유 ★

개발 서버가 **CentOS 7(glibc 2.17)** 인데 `onnxruntime` 휠은 **glibc 2.28** 을 요구합니다.
호스트에 직접 설치할 수 없습니다(2026-08-17 PyPI 확인). 컨테이너는 자기 glibc 를 들고
오므로 상관없습니다. CentOS 7 은 지원도 끝났습니다.

```
onnxruntime 1.28.0  →  manylinux_2_28   ✗  CentOS 7
tokenizers · numpy  →  manylinux2014    ✓
```

### 이미지에 무엇이 들어가나

```
코드(app · scripts) + 파이썬 의존성                      ← 이미지 (710MB)
임베딩 모델 565MB                                        ← 볼륨 (폐쇄망은 이미지 안)
data/ · packs/ · var/ (검수 QA · 문서 · 질문 이력 · 벡터) ← 볼륨
```

이미지 710MB 중 코드는 5MB 뿐이고 나머지는 `onnxruntime` 과 `chromadb` 의 의존성입니다.

**`data/` · `packs/` · `var/` 를 빼는 이유**는 검수 결과와 질문 이력이 쌓이는 곳이라,
컨테이너를 새로 만들어도 남아야 하기 때문입니다. 모델을 빼는 이유는 다릅니다 — 아래.

### 모델은 **이미지에 굽지 않습니다** ★ (2026-10-07)

모델 565MB 는 저장소에 없습니다(`.gitignore` 의 `models/`). 그래서 **git 에서 받아 빌드하는
쪽**(Jenkins)에는 그 폴더가 아예 없고, 예전의 `COPY models/ ./models/` 는 거기서
`"models": not found` 로 멈췄습니다.

쓰는 곳이 둘이고 요구가 반대라 **하나로 정하지 않고 빌드 인자로 갈랐습니다**(`WITH_MODEL`).

| | 개발 서버 (기본) | 폐쇄망 납품 |
| --- | --- | --- |
| 빌드 | `docker build .` | `docker build --build-arg WITH_MODEL=true .` |
| 이미지 | **710MB** | **1.7GB** |
| 모델 | 서버에 한 번 받아 두고 **볼륨** | 이미지 안 |
| 반입물 | 코드(git) + `packs/` + 모델(1회) | **이미지 한 파일** |

개발 서버를 이렇게 하는 이유는 **Jenkins 가 코드만 실어 빌드가 가볍기** 때문입니다. 모델은
거의 바뀌지 않으니 코드를 고칠 때마다 565MB 를 주고받을 이유가 없습니다. 폐쇄망을 반대로
하는 이유는 **반입 절차가 하나여야** 하기 때문입니다 — 볼륨으로 붙이라고 하면 절차가 둘이
되고, 그 하나를 빠뜨리면 컨테이너가 뜨고도 모든 질문이 '미해결'이 됩니다.

#### 모델을 서버에 한 번 받아 두기

서버가 `huggingface.co` 에 닿아야 합니다. 먼저 확인하세요 — 이 한 줄이 `200` 을 내면 됩니다.

```bash
curl -sI -o /dev/null -w '%{http_code}\n' -L \
  https://huggingface.co/gpahal/bge-m3-onnx-int8/resolve/main/tokenizer.json
```

받는 쪽은 **컨테이너 안에서** 돌리는 편이 낫습니다. 같은 스크립트를 쓰므로 파일 이름
바꾸기(`model_quantized.onnx` → `model.onnx`)가 어긋날 일이 없고, CentOS 7 호스트에
파이썬·`httpx` 를 깔지 않아도 됩니다.

```bash
sudo mkdir -p models/bge-m3-onnx && sudo chown -R 10001:10001 models
docker compose run --rm --no-deps \
  -v "$PWD/models:/out" chat \
  python scripts/fetch_onnx_model.py --dest /out/bge-m3-onnx
```

호스트에서 `curl` 로 받아도 됩니다. **이름을 바꿔 저장하는 것**만 틀리지 마세요 — 앱은
`model.onnx` · `tokenizer.json` 두 이름만 봅니다.

```bash
cd models/bge-m3-onnx
B=https://huggingface.co/gpahal/bge-m3-onnx-int8/resolve/main
curl -L -o model.onnx               $B/model_quantized.onnx      # 543.6 MB
curl -L -o tokenizer.json           $B/tokenizer.json            #  16.3 MB
curl -L -o sentencepiece.bpe.model  $B/sentencepiece.bpe.model   #   4.8 MB
```

`docker-compose.yml` 이 이 폴더를 **읽기 전용**으로 붙입니다. 다른 곳에 두었으면
`MODEL_DIR` 로 가리키세요.

```yaml
- ${MODEL_DIR:-./models}/bge-m3-onnx:/app/models/bge-m3-onnx:ro
```

**붙었는지는 `/health/ready` 로 확인합니다.** 안 붙으면 컨테이너는 멀쩡히 뜨고 화면도 뜨는데
**모든 질문이 '미해결'** 로 떨어집니다.

```
embed_model: ok                                   ← 붙었습니다
embed_model: missing: model.onnx, tokenizer.json  ← 볼륨을 보세요
```

#### `chown -R` 을 뒤에서 하지 않습니다 (실측)

레이어는 파일 단위로 쌓이고, **소유자만 바꿔도 그 파일이 새 레이어에 통째로 다시 들어갑니다.**
전에는 Dockerfile 맨 뒤에서 `chown -R appuser:appuser /app` 을 했는데, 모델을 구운 이미지에서
그 레이어 하나가 **598MB** 였습니다(`docker history` 확인) — 565MB 모델이 두 번 들어 있었습니다.

사용자를 먼저 만들고 `COPY --chown` 으로 처음부터 맞추자 **2.71GB → 1.7GB** 가 됐습니다.
폐쇄망 반입물이 1GB 가벼워집니다.

#### 2026-10-07 에 이 PC 에서 확인한 것

| 확인 | 결과 |
| --- | --- |
| 모델 없이 띄우기 | `embed_model: missing: model.onnx, tokenizer.json` · `degraded` |
| 모델 볼륨 붙이기 | `embed_model: ok` |
| 컨테이너 안에서 색인 | 문서 5건 · 청크 35개 · QA 55건 · 벡터 615개 |
| 질문 하나 | `result_type: answer` · 유사도 **0.925** · **21ms** |
| 모델 구운 이미지 | `embed_model: ok` (볼륨 없이) |

## 개발 서버에 올리는 절차 — git → Jenkins (2026-10-07)

**코드는 git 으로, 자료는 손으로 올립니다.** 검수는 운영에서 쌓이므로 코드와 함께 버전
관리하면 배포할 때마다 서버에서 승인한 것이 PC 것으로 덮입니다(`.gitignore` 의 `packs/`).

```
git push ─→ Jenkins 가 build ─→ 컨테이너 교체        코드
scp -r packs/ ──────────────────────────────→ 서버   자료 (694KB)
서버에서 색인 ──────────────────────────────────→    벡터 (파생물)
```

### 처음 한 번만 하는 것

```bash
# ① 모델 — 위 '모델을 서버에 한 번 받아 두기' 참고
sudo mkdir -p models/bge-m3-onnx && sudo chown -R 10001:10001 models
docker compose run --rm --no-deps -v "$PWD/models:/out" chat \
  python scripts/fetch_onnx_model.py --dest /out/bge-m3-onnx

# ② 설정 — .env.server.example 을 복사해 세 가지를 채운다
#    APP_MODE=studio · OLLAMA_HOST=http://<AI 테스트 PC>:11434 · ADMIN_PASSWORD
cp .env.server.example .env && vi .env
```

### 배포할 때마다 하는 것

```bash
# ③ 자료 (바뀌었을 때만). var/ 는 올리지 않는다 — 벡터는 파생물이고,
#    질문 이력까지 덮으면 서버에 쌓인 것이 PC 의 시험 질문으로 바뀐다
scp -r packs/ 사용자@서버:/배포경로/packs/

# ④ 소유자 ★ 안 맞추면 조회는 되는데 승인·설정 저장이 조용히 실패한다
sudo chown -R 10001:10001 data packs var

# ⑤ Jenkins 빌드 (또는 손으로)
docker compose up -d --build

# ⑥ 색인 — packs/ 에는 벡터가 없다. 이걸 빼면 자료 목록은 보이는데 답을 못 한다.
#    **서버가 도는 중이면 앱 안에서** 해야 한다(아래 '밖에서 색인하면' 참고).
curl -u admin:비밀번호 -X POST "http://127.0.0.1:18100/api/admin/qa/reindex?include_docs=true&project=api-manager"
curl -u admin:비밀번호 -X POST "http://127.0.0.1:18100/api/admin/qa/reindex?include_docs=true&project=mcp-manager"

# ⑦ 확인 — status 가 ok 이고 qa_serving 이 0 이 아니어야 한다
curl -s http://127.0.0.1:18100/health/ready
```

⑥ 은 관리자 화면의 **재색인 버튼**으로도 됩니다(프로젝트를 고르고 누르면 그 프로젝트만).

#### 밖에서 색인하면 서버가 500 을 냅니다 ★ (2026-10-07)

`scripts/pack_index.py` 는 **서버를 띄우지 않고** 반입 절차 안에서 돌리라고 만든 것입니다.
서버가 도는 중에 `docker exec` 로 돌리면 **다른 프로세스**가 컬렉션을 지우고 새로 만드는데,
서버는 옛 컬렉션 id 를 쥐고 있어서 그때부터 사용자 화면이 깨집니다.

```
chromadb.errors.InvalidCollectionException: Collection 76b4481c-... does not exist.
```

색인은 멀쩡히 끝나고 색인 로그에도 오류가 없습니다. **화면만 보면 원인을 알 수 없습니다.**

지금은 서버가 이 예외를 받으면 쥔 핸들을 버리고 `503` 과 함께 "다시 시도해 주세요" 를
돌려줍니다 — 다음 요청부터 살아납니다(`app/main.py` 의 `_stale_collection`). 그래도
**도는 중에는 위의 `reindex` 를 쓰세요.** 그쪽은 앱 안에서 돌아 핸들을 스스로 정리합니다.

| 상황 | 쓰는 것 |
| --- | --- |
| 서버가 돌고 있다 | 관리자 화면 `재색인` 버튼 · `POST /api/admin/qa/reindex` |
| 서버를 안 띄웠다(반입 절차) | `python scripts/pack_index.py packs/<프로젝트>` |

⑦ 에서 `qa_serving: 0` 이면 ⑥ 을 안 한 것이고, `embed_model: missing` 이면 ① 의 볼륨이
안 붙은 것입니다. **둘 다 오류를 내지 않습니다** — 화면은 멀쩡히 뜨고 질문만 전부
'미해결'로 떨어집니다.

## 폐쇄망에 반입하는 절차 — 이미지 한 파일

납품처에는 git 도 Jenkins 도 없습니다. **다 만들어진 이미지**만 들어갑니다. 그래서 여기서는
모델을 이미지에 굽습니다(`WITH_MODEL=true`) — 반입 절차가 둘이 되면 그 하나를 빠뜨립니다.

```powershell
# 1) 인터넷이 되는 PC — 모델까지 구워서 빌드하고 여기서 먼저 띄워 확인
docker build --build-arg WITH_MODEL=true -t openapi-chat-serve:latest .
docker run -d --name chat-smoke -p 18101:18100 -e ADMIN_PASSWORD=시험용 `
  -v "c:\chatapp\forever-chat-serve\data:/app/data" `
  -v "c:\chatapp\forever-chat-serve\packs:/app/packs" `
  -v "c:\chatapp\forever-chat-serve\var:/app/var" openapi-chat-serve:latest
#   http://127.0.0.1:18101/health/ready 가 status ok 인지 확인 (모델 적재에 10초쯤)
#   질문도 한 번 던져 봅니다:  POST /api/ask  {"question":"API 등록은 어떻게 하나요?"}
docker rm -f chat-smoke

# 2) 이미지를 파일로 — gzip 은 하지 마세요
docker save openapi-chat-serve:latest -o chat-serve.tar
```

`docker save` 결과는 **이미 압축된 레이어**라 `gzip` 을 걸어도 거의 줄지 않습니다
(2026-08-17 확인). 시간만 더 듭니다.

```bash
# 3) 서버로 옮기고 싣기
scp chat-serve.tar 사용자@서버:/tmp/
ssh 사용자@서버 'docker load -i /tmp/chat-serve.tar'

# 4) 자료를 올리고 소유자를 맞춘다 ★
scp -r packs/ 사용자@서버:/배포경로/packs/
sudo chown -R 10001:10001 data packs var

# 5) 띄우고 색인 — 모델은 이미지 안에 있으니 모델 볼륨은 필요 없다
docker compose up -d
docker compose exec chat python scripts/pack_index.py packs/<프로젝트>
```

### `chown 10001` 을 빼먹으면 ★

컨테이너는 **uid 10001(appuser)** 로 돕니다. 윈도우 개발 PC 에서는 bind mount 가 전부
`rwxrwxrwx` 로 보여 그냥 됐지만, **리눅스 서버에서는 권한이 그대로 넘어갑니다.** 소유자를
안 맞추면 조회는 되는데 질문 이력·승인·설정 저장이 조용히 실패합니다.

### 포트를 127.0.0.1 에만 여는 이유 ★

개발 서버는 **인터넷에 노출돼 있고 SSH 실패 로그인이 2,600건 넘게 관측**됐습니다(아래).
시험 단계에서 굳이 열어 둘 이유가 없습니다. 접속은 터널로 합니다.

```bash
ssh -L 18100:127.0.0.1:18100 사용자@서버
```

`docker-compose.yml` 이 이미 `127.0.0.1:18100` 으로 묶어 두었습니다.

### 처음 띄울 때 막히는 곳

| 증상 | 원인 | 확인 |
| --- | --- | --- |
| 모든 질문이 `unresolved` | 벡터 저장소가 없음 | 재색인 API 한 번 |
| `/health/ready` 가 `degraded` | 모델 파일 또는 승인 QA 없음 | 응답의 `embed_model` · `qa_serving` |
| 기동은 되는데 답이 옛날 것 | `data/` 볼륨이 안 붙음 | `docker compose config` |
| 답은 나오는데 저장이 안 됨 | `data/` 소유자가 10001 이 아님 | `docker exec ... touch /app/data/x` |
| 첫 질문만 10초 | 정상 (모델 적재) | 두 번째 질문이 50ms 이하면 정상 |

1차 프로젝트 것은 [참고/이전프로젝트/deploy/](../참고/이전프로젝트/deploy/) 에 있고
**그 폴더는 실행되지 않습니다** — 전제가 다릅니다(아래 §이전 절차서). 참고만 하세요.

## 이전 절차서가 그대로 안 맞는 이유

`DEPLOY_AIRGAP.md` 는 **단일 서버 + Docker Compose + Jenkins + Ollama 3종** 전제입니다.

| | 이전 문서 | 현재 |
| --- | --- | --- |
| 인프라 | 단일 서버 Compose | AKS (매니페스트 미작성) |
| 오케스트레이션 | Jenkins 파이프라인 | 미정 |
| 컨테이너 | 앱 + Ollama **2개** | **1개** (임베딩이 앱 안에서) |
| 임베딩 | Ollama `bge-m3` 1.1GB | **ONNX int8 565MB, 이미지에 포함** |
| 답변 모델 `qwen3.5:4b` | 3GB | **불필요** |
| 채점 모델 `gemma4` | 9GB | **불필요** (studio 전용) |
| 반입 파일 합계 | 약 13GB | **이미지 1개 (약 1GB)** |
| 서버 메모리 최소 | 8GB | 2GB 수준 |
| `/admin` 인증 | **없음** | 있음 (세션 + Basic) |

**LLM과 Ollama가 통째로 빠집니다.** 모델 반입 절차, `OLLAMA_MAX_LOADED_MODELS` 조정, 모델
교체 시나리오, 사이드카 배치 고민 같은 절이 전부 필요 없어졌습니다. 반입물은 **이미지 하나**
입니다.

그래도 **Compose/Jenkins 절차를 AKS로 옮기는 부분**은 새로 써야 합니다.

## ★ 아직 안 정해진 것 — 파드를 늘릴 때 `data/` 공유

지금은 **파드 1개** 전제라 볼륨 하나면 됩니다. 늘리게 되면 아래를 정해야 합니다.

| 파일 | 성격 | 파드 간 |
| --- | --- | --- |
| `qa_index.json` · `categories.json` · `raw_docs/` · `profile.json` | 읽기 전용 (배포 산출물) | 같아야 함 |
| `chroma/` | 파생 | 파드마다 만들어도 됨 (기동 시간 ↑) |
| `question_log.jsonl` · `question_embeddings.jsonl` | **쓰기** | 합쳐져야 함 |
| `runtime_config.json` | **쓰기** (관리자가 바꿈) | 같아야 함 |
| `analytics.json` · `job_history.json` | 쓰기 | 같아야 함 |

선택지:

- **ReadWriteMany 공유 볼륨** — 가장 단순하지만 JSONL 동시 쓰기 경합을 확인해야 합니다
- **읽기 전용 + 쓰기 분리** — 원본은 이미지에, 쓰기 데이터만 공유 볼륨
- **관리자 전용 파드 분리** — 쓰기는 한 파드만

`SESSION_SECRET` 은 이때 **반드시** 지정해야 합니다 — 안 주면 파드마다 서명 키가 달라
관리자 로그인이 요청마다 풀립니다.

---

## 이미 정해진 것

| 항목 | 값 | 이유 |
| --- | --- | --- |
| `APP_MODE` | **`serve`** | 운영에 GPU가 없습니다. studio 라우터는 403 |
| `SESSION_SECRET` | **반드시 지정** | 안 주면 파드마다 서명 키가 달라 로그인이 풀립니다 |
| `ADMIN_PASSWORD` | **Secret 주입** | 기본값이면 기동 로그에 경고. 파일에 넣지 않습니다 |
| `LOG_FILE` | 기본값 또는 볼륨 경로 | 절대경로를 코드에 박으면 배포가 깨집니다 |
| 옮길 파일 | `qa_index.json` · `categories.json` · `raw_docs/` · `profile.json` | 나머지는 파생물이거나 운영 데이터 |
| `profile.json` | 납품처마다 다름 | 조직명·서비스명·도메인 소개·언어. 없으면 KT 기본값이 나갑니다 |

## 시드 디렉터리 패턴 (아직 안 넣음)

지금 `Dockerfile` 에는 이 패턴이 **없습니다.** `data/` 를 사람이 직접 서버에 올리고
bind mount 하는 방식이라(위 절차 4번) 당장은 문제가 되지 않습니다. **명명 볼륨을 쓰게 되면**
아래 문제가 그대로 생기므로 그때 넣어야 합니다.

이전 프로젝트에서 겪은 문제입니다.

> **Docker 볼륨은 처음 만들어질 때만 이미지 내용을 복사합니다.** 이미지 안 `/app/data` 에
> 문서를 두면 **두 번째 배포부터 문서를 고쳐도 반영되지 않습니다.**

해결:

```
이미지  /app/seed/     ← 원본 (문서·카테고리·QA)
볼륨    /app/data/     ← 운영 데이터

기동 시 entrypoint 가 볼륨에 "없는 파일만" 복사
```

결과적으로 **새로 추가한 문서·카테고리는 다음 배포에 반영되고, 관리자 화면에서 편집한
내용은 보존됩니다.**

강제 초기화가 필요하면 `SEED_FORCE=true` 를 한 번만 켰다 끕니다(켜둔 채로 두면 배포마다
편집 내용이 되돌아갑니다).

## 배포 후 확인

```bash
curl http://<서버>/health          # {"status":"ok"}
curl http://<서버>/health/ready    # embed_model=ok, qa_serving>0, status=ok
curl http://<서버>/api/categories  # groups 가 비어 있으면 안 됩니다
```

브라우저:

- `/` — 챗봇. **입력창 위에 `주제 선택` 버튼이 보여야 합니다** (안 보이면 카테고리가 빔)
- `/admin` — 로그인 모달이 뜨고, studio 전용 탭(⑤⑥⑦)이 **보이지 않아야 합니다**

첫 질문은 임베딩 모델 적재 때문에 느립니다 — 컨테이너에서 **9.7초**를 쟀습니다. 두 번째
질문부터 31~55ms 로 떨어지면 정상입니다.

## 관리자 접근 경로

파이썬 서비스를 내부에만 두면 관리자가 `/admin` 에 들어갈 길을 따로 만들어야 합니다.

- 인그레스에 관리자 경로만 열기 (사내망 IP 제한 권장)
- 또는 포트포워딩 등 운영 도구로만 접근

1차 프로젝트에서 `/admin` 이 무인증이었던 전례가 있으니 **노출면을 늘리지 않는 쪽**을
권합니다.

## 스프링 포털에 챗봇을 붙일 때

포털(`openapi-mng-dev-jdk21`)에서 페이지별로 챗봇을 띄우려는 계획이 있습니다. 방식에 따라
배포 구성이 달라집니다.

| 방식 | 인그레스 | CORS | 파이썬 노출 |
| --- | --- | --- | --- |
| **스프링 서버 경유(프록시)** | 변경 불필요 | 없음 | 내부에만 |
| 인그레스 경로 분리 | 규칙 추가 | 없음 (같은 호스트) | 브라우저에 노출 |
| 브라우저에서 직접 호출 | 규칙 추가 | **CORS 미들웨어 추가 필요** | 브라우저에 노출 |

현재 `app/main.py` 에는 **CORS 미들웨어가 없습니다.** 세 번째 방식을 택하면 추가해야 합니다.

`POST /api/ask` 는 이미 `category_id` · `user_id` · `channel` 을 받으므로, 페이지별
파라미터를 넘기는 데 API 변경은 필요 없습니다.
