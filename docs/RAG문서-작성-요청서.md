# RAG 문서 작성 요청서 (외부 AI용)

> **이 파일을 쓰는 법**
>
> 1. 아래 `---` **다음 줄부터 파일 끝까지** 복사해 AI에게 줍니다
> 2. 맨 아래 **`다룰 주제`** 칸을 채웁니다. 비워 두면 AI가 범위를 멋대로 잡습니다
> 3. 받은 `.md` 파일들을 한 폴더에 모아 올립니다. **`source_files` 에 적힌 원본
>    파일(pptx·pdf·xlsx…)도 같은 폴더에 함께** 넣으면 한 번에 들어갑니다 —
>    본문은 색인되고 원본은 보관돼 사용자가 내려받습니다
>    (올리기 전에 화면 위 **프로젝트 선택기**가 맞는지 확인하세요)
> 4. 그다음 [카테고리-작성-요청서.md](카테고리-작성-요청서.md) → [QA-생성-요청서.md](QA-생성-요청서.md)
>    순서로 받습니다
>
> **문서를 먼저, QA를 나중에** 받는 순서가 중요합니다. QA는 확정된 문서를 근거로 만들어야
> 하고, 문서가 바뀌면 QA의 출처가 어긋납니다.
>
> 사람이 읽는 가이드를 그대로 넣지 마세요. 가이드는 처음부터 끝까지 읽는 글이고 이쪽은
> **절 단위로 잘려 검색되는** 글입니다. 같은 내용이라도 다시 쓰게 해야 합니다.

사내 FAQ 챗봇이 검색할 **원본 문서**를 마크다운으로 작성해 주세요.

## 이 문서가 어떻게 쓰이는가

챗봇은 문서를 통째로 읽지 않습니다. **`##` 소제목 사이를 한 조각으로 잘라** 각각을 따로
검색합니다. 사용자 질문과 가장 가까운 조각이 걸리고, 그 조각의 내용으로 답이 나갑니다.

그래서 **소제목 하나 = 질문 하나** 라고 생각하고 나누면 됩니다.

## 1. 파일

| 규칙 | 내용 |
| --- | --- |
| 형식 | 마크다운 `.md` · 인코딩 **UTF-8** |
| 파일 이름 | **영문 소문자 · 숫자 · `-`** 만. 예: `api-register-process.md` |
| 문서 ID | **파일 이름이 곧 문서 ID 입니다.** 따로 적지 않습니다 |
| 분량 | 주제 하나에 파일 하나. 소제목이 10개를 넘으면 나눕니다 |

**앞머리(frontmatter)를 맨 위에 넣습니다.**

```markdown
---
title: API 등록 · 배포 절차
category: 이용가이드 > 절차
source_files: [2026_하반기_API가이드_v3.pptx, 등록항목_정리.xlsx]
url: /v2/apiops/usage-guide/process
updated: 2026-10-06
---
```

| 항목 | 필수 | 설명 |
| --- | --- | --- |
| `title` | **필수** | 검색 결과 카드에 그대로 나옵니다. 사용자가 읽을 이름으로 |
| `category` | **필수** | `대분류 > 소분류`. 사람이 문서를 분류해 보는 데 씁니다 |
| `source_files` | **원본을 보고 썼다면 필수** | 아래 설명 |
| `url` | 권장 | 그 기능의 실제 화면 주소. 답변에서 바로 가기로 쓰입니다 |
| `updated` | 권장 | `YYYY-MM-DD` |

### `source_files` — 무엇을 보고 썼는지 적어 주세요 ★

이 앱은 **두 가지 자료를 나눠서** 다룹니다.

```
.md          AI 가 읽고 답하는 것. 검색·색인 대상
원본 파일     사람이 내려받아 보는 것 (pptx · pdf · docx · xlsx · hwp)
```

`.md` 를 **발표자료나 보고서를 보고** 썼다면, 그 파일 이름을 `source_files` 에 그대로
적어 주세요. 답변에 그 문서가 인용될 때 사용자가 **원본을 바로 내려받을 수 있습니다.**

- **파일 이름을 그대로** 적습니다. 확장자까지 적는 쪽이 정확합니다
- **여러 개면 쉼표로** 나열합니다 — 발표자료와 정산표를 함께 보고 썼다면 둘 다 적습니다
- **한 원본을 여러 `.md` 가 나눠 써도 됩니다.** 긴 발표자료를 주제별로 쪼갤 때 각 파일에
  같은 원본을 적으면 됩니다
- 원본 없이 새로 쓴 문서면 **적지 않습니다.** 없는 파일을 적으면 그냥 무시됩니다

> `.md` 파일 이름과 원본 파일 이름이 **똑같으면** 적지 않아도 자동으로 묶입니다
> (`api-등록.md` ↔ `api-등록.pptx`). 하지만 실제 원본 이름은 보통 그렇지 않으므로,
> **적어 주시는 편이 확실합니다.**

**`doc_id` 는 쓰지 마세요.** 이 앱은 파일 이름을 ID로 씁니다. 앞머리에 적으면 무시되고,
나중에 "ID를 지정했는데 왜 다른 값이지"로 헷갈립니다.

## 2. 구조 — 여기가 가장 중요합니다

1. **`##` 소제목을 자주 답니다.** 그것이 검색 단위입니다. 한 문서에 3~9개가 적당합니다.
2. **한 절은 120~800자.**
   - 120자 미만: 너무 짧아 엉뚱한 질문에도 걸립니다 (첫 소제목 앞 도입부는 예외)
   - **1,800자 초과: 뒷부분이 조용히 버려집니다.** 오류가 나지 않아 아무도 모릅니다
3. **한 절에 한 주제.** '등록 절차'와 '필수 입력 항목'을 한 절에 섞으면, 필수 항목을 묻는
   질문이 절차 설명에 묻혀 안 걸립니다.
4. `###` 은 `##` 아래 세부 항목에만 씁니다. 검색에서 `부모 > 자식` 으로 표시됩니다.
5. 첫 소제목 앞에 **도입부 1~2문장**을 둡니다. 이 문서가 무엇을 다루는지 적습니다.

### 절 머리에 예상 질문을 적으면 좋습니다 (권장)

소제목 바로 아래에 그 절로 답할 수 있는 질문들을 한 줄로 적어 주세요. 사용자가 쓰는 표현이
검색에 함께 들어가 적중률이 올라갑니다.

```markdown
## 전체 흐름과 역할

질문: 전체 절차가 어떻게 되나요 / 등록부터 운영 배포까지 순서 / 누가 승인하나요

API 는 **등록 → TB 배포 → 테스트 → 운영 배포** 네 단계를 차례로 거칩니다.
```

- `질문:` 으로 시작하고 ` / ` 로 구분합니다. 3~5개
- **질문만 적고 답을 적지 않습니다.** 답은 그 아래 본문입니다

## 3. 쓰는 법

- **사용자가 묻는 말로 소제목을 답니다.** `개요`·`설명` 보다 `API 등록 절차`·`등록이 실패할 때`
- 화면명 · 버튼명 · 메뉴 경로 · 필드명은 **실제 화면에 적힌 그대로** 씁니다. 답변에 그대로 나갑니다
- 절차는 번호 목록으로 씁니다
- 표가 길어지면 나눕니다. 표 앞에 한두 문장으로 무엇에 대한 표인지 적습니다
  (표만 있는 절은 검색이 잘 안 걸립니다)
- 조건·예외는 "~면 ~합니다" 로 분명히 적습니다. 사용자는 대개 예외 상황에서 묻습니다

## 4. 쓰지 말아야 할 것

| 금지 | 이유 |
| --- | --- |
| 이미지 `![](img/x.svg)` | 파일 경로가 검색에 섞이고 답변에도 그대로 나갑니다 |
| `[[문서ID]]` 참조 표기 | 내부 표기라 답변에 섞이면 사용자가 읽을 수 없습니다 |
| "위에서 설명한" · "아래 참조" · "앞서 본" | **절은 따로 떨어져 검색됩니다.** 앞뒤가 없는 답이 나갑니다 |
| "이 문서에서는 ~를 설명합니다" | 사용자는 문서가 아니라 업무 절차를 묻습니다 |
| 추측 · 일반론 | 모르면 적지 않습니다. 없는 기능을 지어내면 그대로 사용자에게 나갑니다 |

## 5. 예시

````markdown
---
title: API 등록
category: API 관리 > API 등록
url: /api/spcreg/def/mvApiDefReg.do
updated: 2026-10-06
---

# API 등록

API Manager 에서 개별 API(Method + Path)를 그룹 안에 추가하는 화면입니다. 등록한 API는
검증을 거쳐 배포를 신청하면 외부에 공개됩니다.

## API 등록 절차

질문: API 등록은 어떻게 하나요 / 등록 순서 알려주세요 / 새 API 추가하는 방법

1. 좌측 메뉴에서 `API 관리 > API 등록` 을 엽니다.
2. 대상 **API 그룹(SPC)** 을 고릅니다. 그룹이 없으면 그룹을 먼저 등록해야 합니다.
3. API 명, Path, Method 를 입력하고 `저장` 을 누릅니다.
4. 저장한 API는 `검증 대기` 상태가 되며, 검증을 통과해야 배포를 신청할 수 있습니다.

## 등록할 때 꼭 입력해야 하는 항목

질문: 필수 입력 항목이 뭔가요 / Path 는 어떻게 적나요 / Method 종류

| 항목 | 설명 |
| --- | --- |
| API 명 | 목록에 표시되는 이름입니다. 같은 그룹 안에서 중복될 수 없습니다 |
| Path | `/` 로 시작합니다. 경로 변수는 `{변수명}` 으로 적습니다 |
| Method | GET · POST · PUT · DELETE 중 하나입니다 |

## 등록이 실패할 때

질문: 저장이 안 돼요 / 중복 오류가 납니다 / 같은 Path 를 또 등록하려면

같은 그룹에 **같은 Method + Path 조합**이 이미 있으면 저장되지 않습니다. 기존 API를
수정하거나 Path 를 다르게 지정해야 합니다.
````

## 6. 내보내기 전에 확인

- [ ] 모든 문서에 `title` · `category` 가 있습니까? `doc_id` 를 적지 않았습니까?
- [ ] 원본(pptx·pdf·xlsx…)을 보고 쓴 문서에 `source_files` 를 적었습니까? 파일 이름이
      실제와 **글자까지 같습니까?**
- [ ] 한 절이 1,800자를 넘지 않습니까? 넘으면 소제목으로 나눕니다
- [ ] 소제목만 읽어도 무엇을 다루는 문서인지 알 수 있습니까?
- [ ] "위에서 설명한" 처럼 **다른 절을 전제로 하는 문장**이 없습니까?
- [ ] 이미지와 `[[문서ID]]` 가 본문에 없습니까?
- [ ] 문서에 **실제로 있는 내용**만 적었습니까? 추측한 부분은 없습니까?

## 7. 내보내는 방법

파일마다 **파일 이름을 먼저 적고** 그 아래 전체 내용을 코드 블록으로 주세요.
**한 번에 3~5개씩** 나눠 주시면 됩니다 — 한 번에 다 쓰려고 하면 뒤쪽 문서가 짧아집니다.

```
파일: api-register-process.md
(내용 전체)

파일: api-register-fields.md
(내용 전체)
```

마지막에 **만든 문서 목록**(파일 이름 · 제목 · 소제목 수)을 표로 정리해 주세요. 다음 단계인
QA 작성에서 그 목록을 그대로 씁니다.

## 9. 근거 자료

**원본 파일 이름을 먼저 적고** 그 아래에 내용을 붙여넣어 주세요. 그 이름이 그대로
`source_files` 에 들어가고, 사용자가 답변에서 **원본을 내려받는 데** 쓰입니다.

```
[원본] 2026_하반기_API가이드_v3.pptx
(여기에 그 파일의 내용을 붙여넣으세요)

[원본] 등록항목_정리.xlsx
(여기에 그 파일의 내용을 붙여넣으세요)
```

- 파일 이름은 **확장자까지 그대로** 적습니다. 글자가 하나라도 다르면 짝이 맺히지 않습니다
- 원본 파일이 따로 없고 그냥 설명을 적어 주는 것이라면 `[원본]` 줄 없이 붙여넣으세요.
  그 경우 `source_files` 는 적지 않습니다
- **이 안에 있는 내용으로만 작성합니다.** 여기 없는 것은 지어내지 않습니다
